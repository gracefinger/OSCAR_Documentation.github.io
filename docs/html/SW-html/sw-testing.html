    Testing

    Testing Across OSCAR Ground Station

    This page describes every kind of testing used on OSCAR Ground Station: unit, integration, regression, automated (CI/CD), and acceptance testing. Some of it is built into the desktop app and some is run by developers from a terminal or by the GitLab pipeline. For how the testing cards on the Error Logging page work internally, see the Error Logging documentation.

    Testing Integrated Into OSCAR Ground Station

    From the desktop app, users can run hardware-in-the-loop integration and regression tests without leaving Ground Station. These are available from the Integration & Regression Testing card on the Error Logging page. With a flight controller connected over USB, users can:

    • Select test groups. Read commands, Settings, and Streaming are on by default. Calibration & reset and Motors are off by default, and enabling either one triggers a confirmation dialog. Motor tests must only be run with propellers removed.
    • Run the full communication chain. Each test exercises the UI, window.backendAPI, the C addon, USB, and the firmware, then the path back.
    • Watch live results. Each row shows PASS, FAIL, or SKIP, round-trip time, attempts, retries, and a response preview. Yellow rows flag retries, port re-scans, or known quirks.
    • Stop a run early. Stop Tests halts the run after the current call.
    • Review aggregate statistics. These include pass rate, packet-level USB accuracy, first-try success, retry counts, latency (avg, median, p95, min, max), slowest calls, known quirks, failures, and skips.
    • Diagnose failures. The Ground Station Debug Log above the card shows the underlying WARNING and ERROR entries.
    • Save a report. Save Test Results downloads oscar-integration-tests-<timestamp>.txt. Saved reports act as baselines for regression comparison and as evidence for acceptance testing.

    Testing Not Integrated Into OSCAR Ground Station

    Some testing was implemented for the project but is not available from the desktop app. It is run by developers from a terminal or by the GitLab pipeline.

    What We Did

    • Unit tests using Node's built-in node:test framework, located in Software/OSCAR-app/test/. They use mocked backend APIs (window.backendAPI), mocked DOM elements, and VM-based test harnesses, so no flight controller is needed. Current areas are configuration import validation, configuration state restoration, load and save workflows, and Electron process boundaries.
    • Code coverage measurement with c8, split into three scopes: application, UI-only, and Electron process-boundary. Each is run with its own npm run test:*-coverage script.
    • Automated CI/CD testing through GitLab (.gitlab-ci.yml). On every push or merge request, the pipeline installs dependencies with npm ci --ignore-scripts, runs the tests and coverage commands, and publishes a Cobertura coverage report. The application coverage percentage is used as GitLab's primary figure.
    • Manual pre-release checks for Calibration and Motors with props removed.

    These are not exposed in the app because they are developer-facing. They test application logic without hardware, which makes them suited to fast, repeatable checks during development rather than end-user operation.

    What We Did Not Do But Could Be Useful

    • Automated end-to-end UI tests. Driving the real Electron window (for example with Playwright's Electron support) would catch problems that mocked DOM tests can't.
    • Hardware-in-the-loop CI. The integration tests currently need a physical flight controller and are run manually. A self-hosted Windows runner with a connected controller could run them automatically on each merge.
    • Automated report comparison. Baseline and new integration reports are currently compared by hand. A script or in-app diff view could flag new FAILs, increased retries, or latency regressions automatically.
    • Enforced coverage thresholds. Coverage is reported but not required to meet a minimum, so a significant drop wouldn't fail the pipeline on its own.
    • Windows CI runners. The app only works on Windows, but CI runs on Linux with --ignore-scripts, so native C addon builds are not verified in CI.
    • Fault-injection tests. Examples are USB unplug and replug mid-run, corrupted or partial packets, and a controller that stops responding.
    • Stream data validation. Streaming tests count packets but do not check that values are plausible.
    • Packaging and installer smoke tests. These would confirm that a built release launches and detects hardware.
    • In-app access to unit tests. A button to run the unit suite and show results could help users who don't have a development environment.

    Unit Testing

    Overview

    According to GeeksforGeeks, "Unit Testing is a software testing technique used to verify individual units of source code, such as methods, functions, or classes, in isolation." Unit testing ensures that each module behaves according to its requirements and helps prevent new features from regressing older ones. This section explains how unit testing is done in an npm environment for OSCAR Ground Station.

    For our purposes, unit testing does not interact with any real flight-controller hardware. See Integration Testing for end-to-end testing. The unit tests focus on the desktop application's user interface behavior.

    OSCAR Ground Station uses Node.js's built-in node:test framework, which makes the process simple and reproducible. Tests use mocked backend APIs to simulate Electron, browser, and flight-controller responses and verify that frontend UI behavior aligns with expectations.

    Current testing areas include (work in progress):

    Test Area File Name (inside /test folder)
    Configuration File Import Validation configurationImport.test.js
    Configuration State Restoration configurationState.test.js
    Load & Save Workflows loadAndSave.test.js
    Electron Process Boundaries processBoundaries.test.js

    Unit tests can run in a GitLab CI pipeline without being connected to a flight controller. See Automated Testing and CI/CD for more. They can also be run locally in a terminal with the command npm test.

    Code Implementation Necessary

    To add test files of your own, navigate to the Software/OSCAR-app/test/ folder. You can use Node's built-in testing modules:

    const { describe, it } = require("node:test");
    const assert = require("node:assert/strict");

    Rather than connecting to a real flight controller, we use mocked versions of the backend API (window.backendAPI) to simulate flight-controller responses. We can also mock browser objects, such as the window, document, DOM (Document Object Model) elements, dialogs, file inputs, and more.

    When testing page scripts that normally depend on a browser, we use test harnesses. A test harness is the supporting code around a test that creates a controlled environment for the code being tested. For example, configurationState.test.js creates:

    • MockElement to act like an HTML input, checkbox, or select.
    • A mock document with querySelectorAll() and createElement().
    • A mock window.sessionStorage.
    • A mock window.backendAPI.
    • A VM context in which the real application script can run.

    How to Write Unit Tests

    Identify Behavior to Test

    Review each page and identify:

    • Inputs and outputs
    • Buttons and user interactions
    • Backend API calls
    • Error handling
    • Default values
    • Invalid input behavior

    Begin with logic that does not require rendering or hardware.

    Create a Test File

    1. Create the File: Create a <test_file_name>.test.js file in the test directory.
    2. Build the Harness: Create the test harness, if necessary.
    3. Group Tests: Group related tests with describe.
    4. Write Cases: Write individual cases with it, using clear names that describe the expected behavior.
    describe("configuration state", () => {
      it("restores cached checkbox values", async () => {
        // Arrange, act, and assert
      });
    });

    Arrange the Test

    • Create mock cached settings, backend responses, or DOM elements. For example, provide a cached motor configuration or a mock configuration file.
    • Set up the expected initial state.

    Act on the Application Logic

    Call the function being tested, or simulate a button click, file selection, dialog confirmation, or backend response. Examples:

    • Restore cached settings.
    • Import a configuration file.
    • Confirm a save dialog.
    • Reject an invalid number.
    • Simulate a controller write failure.

    Assert the Result

    Use assertions to verify the expected behavior. Examples:

    • A value was restored to a form control.
    • An error was thrown.
    • A backend command was called with the correct arguments.
    • A dialog was canceled without saving.
    • A status changed to "Partially applied."
    • An unsupported setting was skipped.

    Run Tests Locally

    From the OSCAR app directory (Software/OSCAR-app), run a specific test file:

    $ node --test test\configurationState.test.js

    Run the entire test suite:

    $ npm test

    Confirm that all tests pass, and investigate any failure before adding or merging additional changes.

    Run Coverage Locally

    $ npm run test:application-coverage
    $ npm run test:ui-coverage
    $ npm run test:process-coverage
    • Application coverage includes the broader JavaScript application logic.
    • UI-only coverage excludes main.js, preload.js, and addonWorker.js.
    • Process-boundary coverage measures those Electron-specific files separately.

    Add the Tests to CI

    GitLab runs the application coverage command from .gitlab-ci.yml. Because the command uses node --test, test files ending in .test.js are automatically discovered, so new tests generally do not need to be listed individually in the YAML file. The CI job:

    • Installs dependencies
    • Runs all tests
    • Generates coverage
    • Extracts the application line-coverage percentage
    • Publishes the Cobertura coverage report

    Review the Results

    • Confirm the total number of tests increased.
    • Confirm all tests passed.
    • Check whether the relevant source file's coverage increased.
    • Make sure the coverage percentage is labeled accurately.

    Note: Coverage measures executed code, not whether every possible user scenario has been tested.

    Integration Testing

    Overview

    Integration testing checks that the full chain works end to end: Ground Station UI, then window.backendAPI, then the C addon (USBCommunication.c), then USB, then the firmware, and back. It runs on real hardware from the Integration & Regression Testing card on the Error Logging page.

    For each call, the runner records:

    • Verdict: pass, fail, or skip.
    • Round-trip time: from the frontend call to the response being received.
    • Attempts and retries: inferred from the "Attempt N..." log lines that write_to_port() emits, since the C addon doesn't return them.

    At the end it prints aggregate statistics: pass rate, packet-level USB accuracy, first-try success, retry counts, latency (avg, median, p95, min, max), the slowest calls, known quirks, failures, and skips.

    Tests are organized into groups, selectable with the checkboxes:

    Group What it does Default
    Read commands Getter commands only Always on
    Settings Reads a value, then writes the same value back (no net change) On
    Streaming Starts each stream, counts packets for 2 s, then stops On
    Calibration & reset ⚠ Calibration and reset commands, which can overwrite stored data Off
    Motors ⚠ Motor commands (props OFF) Off

    Other behavior:

    • Enabling Calibration or Motors triggers a confirmation dialog.
    • A failed GetConnection preflight aborts the run so it doesn't trigger a port scan on every call.
    • NotARealCommand is a deliberate negative test that must return an error. It is excluded from all statistics.
    • Stop Tests halts after the current call.

    Code Implementation - Integration Tests

    One-Time Wiring

    • log.js forwards every incoming entry to logTaps inside appendLogEntry.
    • log.html loads log.js before integrationTests.js.
    • The preload exposes populateAll, updateValue, startStreaming, stopStreaming, onStreamData, offStreamData, and onLogData on window.backendAPI.
    • The page contains #integrationOptions, #integrationTestStatus, #integrationTestResults, #runIntegrationTests, and #saveIntegrationResults.

    Updating the Test Plan

    Whenever the firmware or software changes, update the test plan (INTEGRATION_TESTS):

    Change What to update
    New read command Add { group: "read", kind: "populate", command, expect: [...] }
    New write command Add a kind: "update" entry with payload and expect
    New writable setting Add a kind: "roundtrip" entry with source.command and source.keys, plus valueMap or numericOnly if needed
    New stream Add a kind: "stream" entry, plus extraStop and extraExpect if it has its own stop command
    Renamed or removed JSON keys Fix the expect lists and the keys in roundtrip source
    Changed log messages in the C code Update the IT_*_TERMINALS regexes, or retry counts will show as "n/a"
    Changed meter source dropdown text Update IT_METER_SOURCE_MAP

    expect syntax:

    • "Key" means the key must exist anywhere in the response.
    • "Key=Value" means the key must exist and equal the value (case-insensitive).
    • Any miss fails the test.

    quirk field: use it for a response that passes today but looks wrong. It shows as a warning in the row and summary. When the firmware is fixed, the expect check will start failing, so update expect and remove quirk.

    Tunable constants:

    • IT_STREAM_SAMPLE_MS
    • IT_STREAM_MIN_PACKETS
    • IT_LOG_TIMEOUT_MS
    • IT_PREVIEW_CHARS

    Notes

    • Setup, log levels, and filtering are covered in the Error Logging documentation. The integration runner relies on the same log pipeline (TIMING, WARNING, and ERROR entries drive the retry and timing readouts).
    • The command spelling GetFrimwareVersion is intentional. It matches map_command(), so don't "fix" it in the test plan alone.
    • Retries are inferred from logs, not returned by the addon. If log forwarding is unavailable, attempts show as "n/a" and count as a single attempt in the statistics.
    • The Settings group writes back the current value. If a field reports display text instead of the raw value, the test is skipped rather than writing a guess to the drone.
    • Never run Motors or Calibration with propellers attached.

    How to Use This Feature

    1. Connect: Connect the drone over USB and open Error Logging.
    2. Power Check: Make sure the flight controller is powered and Ground Station can see it.
    3. Choose Groups: In Test Groups, leave the defaults (Read, Settings, Streaming), or tick Calibration and Motors if you need them. For Motors, remove all props first.
    4. Run: Click Run Integration Tests.
    5. Watch Results: Each row shows PASS or FAIL, time, attempts, retries, and a response preview. Yellow rows indicate retries, a port re-scan, or a known quirk.
    6. Read Statistics: Review the Statistics block at the end.
    7. Diagnose: Check the Ground Station Debug Log above for the underlying WARNING and ERROR entries on any failure.
    8. Save: Click Save Test Results to download oscar-integration-tests-<timestamp>.txt.
    9. Stop Early: Click Stop Tests (it stops after the current call).

    Regression Testing

    Overview

    Regression testing confirms that new work hasn't broken existing behavior. For OSCAR that means any change to firmware commands, JSON structure, the C addon, backendAPI, or UI logic should leave previously passing tests passing, with latency and retry behavior not noticeably worse. The same test plan is rerun before and after each change and the results compared.

    How the Unit Testing Setup Covers This

    Unit tests provide a fast way to check that individual functions and application behaviors continue working after changes are made. Existing tests should be rerun after every update to verify that previously supported behavior has not changed unexpectedly. These tests can confirm that:

    • Firmware command names are sent correctly through backendAPI.
    • JSON responses are parsed and mapped to the correct UI fields.
    • Missing or malformed responses are handled properly.
    • Configuration values are validated before being sent to the flight controller.
    • Retry, failure, and partial-application behavior remains consistent.

    Because the tests use mocked backend responses, firmware and controller failures can be tested without connecting real hardware. When a new command, JSON field, or user-facing behavior is added, a corresponding unit test should also be added. If an existing test fails after a change, that may indicate a regression or an intentional behavior change that needs to be documented. Unit tests do not replace integration tests; they validate application logic and API boundaries, while integration tests verify communication with the actual firmware and hardware.

    How the Integration Testing Features Cover This

    The integration runner is the firmware/software communication layer and software IPC layer regression suite:

    • expect checks are the regression assertions. If a firmware change renames or drops a JSON key, the test fails with "unexpected response: missing key ...".
    • The negative test guards against error handling silently breaking.
    • quirk entries track known-bad behavior so it doesn't get forgotten, and they flip to failures once fixed.
    • Saved reports serve as baselines. Compare pass rate, packet-level accuracy, first-try success, retries, p95 latency, and slowest calls between runs. A rise in retries or latency is a regression even when everything still passes.
    • Updating the plan when commands or JSON values change is part of the regression process, so the suite doesn't produce misleading results.

    How CI/CD Can Be Used for Regression Testing

    GitLab CI/CD automatically runs the project's tests whenever changes are pushed or submitted through a merge request. This provides a consistent regression check in a clean Node.js environment instead of relying only on a developer's local computer. The pipeline installs the project dependencies, runs the unit tests, measures application, UI, and process-boundary coverage, and publishes the resulting Cobertura coverage report. The pipeline should fail when a test fails or when a required coverage command cannot complete, helping prevent regressions from being merged.

    CI results should be reviewed for more than simple pass-or-fail status. Test count, failed or skipped tests, coverage percentage, retry count, first-attempt success rate, latency, and slowest operations should also be considered. A regression may exist even when all tests pass if latency increases, retries increase, coverage drops significantly, or the test plan no longer reflects the application's current commands and JSON structure.

    Steps to Run a Regression Check

    1. Baseline: On a known-good firmware and software build, run the integration tests and save the report.
    2. Unit Tests: Run unit tests locally after making changes.
    3. Update the Plan: Update the test plan if you added or changed commands or JSON keys (see Updating the Test Plan).
    4. Rerun: Run the integration tests again on the new build with the same groups, and save the report.
    5. Compare: Compare the two reports.
      • Any new FAIL or SKIP is a regression.
      • Look for increases in retries or latency, or drops in first-try success.
      • Check whether any quirk notes disappeared or turned into failures.
    6. Investigate: Use the row's response preview and the Ground Station Debug Log to investigate failures.
    7. Fix and Keep: Fix, rerun, and keep the final report with the release or pull request.
    8. Pre-Release: Before a release, also run Calibration and Motors manually with props removed.

    Automated Testing and CI/CD

    According to GeeksforGeeks, "Automation Testing is a software testing approach in which test cases are executed using tools and scripts instead of being performed manually." CI/CD stands for Continuous Integration and Continuous Delivery (or Deployment). These concepts are closely related because automated testing is often included in CI/CD pipelines to verify that new code changes do not break existing functionality. In this project, GitLab CI/CD automatically runs the OSCAR Ground Station's test suite whenever changes are pushed or submitted for review. This provides faster feedback, improves consistency, and helps ensure that only tested and validated code is merged into the project.

    Overview

    The GitLab CI/CD pipeline configuration is defined in .gitlab-ci.yml. The pipeline currently contains an application coverage job that:

    • Uses a Node.js 22 environment.
    • Installs the project dependencies.
    • Runs the automated tests.
    • Measures application, UI, and process-boundary coverage.
    • Publishes the application coverage report.

    Tests use Node.js's built-in node:test framework (see Unit Testing). Code coverage is measured with the c8 JavaScript library, which needs to be added as a development dependency in package.json.

    Code coverage should be described as:

    • Application JavaScript line coverage.
    • UI-specific JavaScript line coverage.
    • Electron process-boundary line coverage.

    These percentages should not be described as coverage of the entire project or entire codebase, so as not to be misleading.

    The project's test scripts are also defined in package.json. The main scripts include:

    npm test
    npm run test:ui-coverage
    npm run test:application-coverage
    npm run test:process-coverage

    Note: When source files are loaded through a VM for testing, the real source path should be provided so c8 attributes coverage to the correct file. For example, in loadAndSave.test.js:

    const sourcePath = require.resolve("../Components/loadAndSave");
    const source = fs.readFileSync(sourcePath, "utf8");

    vm.runInNewContext(
      `${source}\nglobalThis.loadSaveTestHooks = {
        collectCurrentConfiguration,
        refreshConfigurationPreview,
        importConfigurationFile
      };`,
      context,
      { filename: sourcePath }
    );

    The filename option tells c8 which source file the code comes from, so that it can determine the percentage of code covered by tests in the original file. Add generated coverage directories to .gitignore so reports are not accidentally committed.

    Code Implementation Necessary

    In addition to following the Code Implementation steps for Unit Testing, the tests can be added to your CI/CD pipeline. Add your test scripts to the scripts section of package.json. Also be sure you've added the required testing and coverage packages (c8) to your devDependencies. Make sure that you update package-lock.json anytime your dependencies change. (You may also need to run npx electron-rebuild to update the native C module.)

    Next, configure your GitLab pipeline in .gitlab-ci.yml to:

    • Select a Node.js image.
    • Move into the OSCAR application directory.
    • Install dependencies with npm ci.
    • Run the test scripts.
    • Extract the desired coverage percentage.
    • Publish coverage artifacts.

    Since the current application only works in a Windows environment, you can use --ignore-scripts in CI when installation scripts attempt to build Windows-only native dependencies in the Linux CI environment.

    Make sure to configure c8 coverage scopes carefully:

    • UI coverage excludes main.js, preload.js, and addonWorker.js.
    • Process-boundary coverage includes those Electron-specific files.
    • Application coverage includes the broader Components JavaScript files.

    Steps to Run It

    1. Create or Update Tests: Write tests and generate test coverage (see How to Write Unit Tests).
    2. Push: Push the changes to GitLab.
    3. Pipeline Starts: GitLab reads .gitlab-ci.yml, creates the configured test job, uses the specified Node.js environment, changes into Software/OSCAR-app, and runs npm ci --ignore-scripts.
    4. Coverage Runs: The pipeline runs npm run test:application-coverage, npm run test:ui-coverage, and npm run test:process-coverage.
    5. Report Publishes: c8 generates a Cobertura XML report, and GitLab uploads it as a coverage artifact. The report can be viewed from the pipeline or job results and provides file-level coverage details in addition to the overall percentage.
    6. Review Failures: If the pipeline fails, open the failed GitLab job and review whether the failure came from dependency installation, a failed test, coverage command configuration, coverage percentage parsing, or missing coverage artifacts. Fix the issue locally, run npm test and the relevant coverage command again, then push the correction and allow GitLab to run a new pipeline.
    7. Merge After Validation: Confirm the pipeline passes, all automated tests pass, and the coverage report has been reviewed. Verify that the coverage percentage is labeled according to its scope. Merge only after the required CI checks succeed.

    Note: The application coverage value is used as GitLab's primary coverage percentage. UI and process-boundary values are printed separately in the job log. This prevents GitLab from incorrectly averaging coverage percentages from different test scopes.

    Acceptance Testing

    Overview

    Acceptance testing is the final check that a build meets its requirements and is ready for release or merging. The unit, integration, and regression tests described above verify that the software works. Acceptance testing uses their results, plus some manual user checks, to decide whether a given build is good enough to ship.

    A build is accepted when all of the criteria below are met. If any are not, the failure should be investigated and either fixed or documented as a known issue before release.

    Integration

    Integration acceptance is based on a saved report from the Integration & Regression Testing card, run on real hardware. A build is accepted when:

    • The report can be successfully saved.
    • There are no unexpected FAIL results.
    • There are no unexplained SKIP results. A skip is acceptable only if its cause is understood (for example, the field reports display text instead of the raw value).
    • NotARealCommand returned an error as intended.
    • Retry counts and latency (avg, p95) are not noticeably worse than the baseline.

    Unit

    Unit acceptance is based on the automated test suite and the CI pipeline. A build is accepted when:

    • npm test passes with no failed tests.
    • The GitLab pipeline completes successfully, including all three coverage commands.
    • The test count has not decreased.
    • The coverage report was published, and coverage did not drop significantly. Coverage should be labeled by scope (application, UI, or process-boundary), not as coverage of the whole project.

    Regression

    Regression acceptance compares the new build against a known-good baseline. A build is accepted when:

    • No test that passed in the baseline now fails or is skipped.
    • Pass rate, packet-level USB accuracy, and first-try success are equal to or better than the baseline.
    • Retries, p95 latency, and the slowest calls have not noticeably increased.
    • Any quirk that disappeared was an intentional firmware fix, and the test plan was updated to match.
    • The test plan reflects the current commands and JSON structure, so the results are not misleading.
