    Error Logging

    Error Logging & Data Flow

    Overview

    This section explains how error logging works in OSCAR Ground Station and how the Error Logging page uses it. For the USB command path that most of these logs describe, see the Backend USB Communication and Frontend USB Communication documentation. Those documents only mention the logging additions to the C file briefly and point back here for the details. A separate testing documentation gives an overview of every testing method and how to use each one; this document covers how the testing cards on this page work internally.

    We will start with the two kinds of logs and the overall flow of a log entry (this part includes the C module). Then we will go through the logging code in the C module, the worker and IPC layers that carry entries to the window, the page itself (layout, filtering, saving, display limits), the Integration & Regression Tests card, the firmware Flight Logs, the Onboard Firmware Unit Tests card, and finally how the logging system behaves when something goes wrong.

    The Error Logging page has five cards:

    Card What it is for
    About Logs & Testing Explains the page to the user
    Onboard Flight Logs Logs the firmware stored in its EEPROM, requested with a button
    OSCAR Ground Station Debug Log Live history of what the desktop app logs about itself
    Integration & Regression Tests Runs the firmware commands end to end and reports results
    Onboard Firmware Unit Tests Triggers tests built into the firmware to be run, then displays the output and results

    The Two Kinds of Logs

    OSCAR Ground Station Debug Log (desktop side). Everything OSCAR Ground Station records about its own operation, almost all of it from the C communication layer: finding and verifying COM ports, sending commands, retries, CRC failures, timing, and starting and stopping the stream. Entries are created while the app runs, pushed to the page live, and kept only for the current session.

    Onboard Flight Logs (firmware side). Events the drone recorded for itself and saved in its own EEPROM, including times when it was not connected to the desktop app. These are not streamed. The user requests them with a button, and they never touch the C log queue or the log worker described below.



    Note: A FW tag on a Debug Log entry does not mean the entry came from the Flight Logs. It means the desktop app noticed the firmware misbehaving while talking to it (a short read, a bad CRC, an unexpected header). Flight Logs are history stored on the drone.

    Debug Log Data Flow

    This flow applies to the OSCAR Ground Station Debug Log. The Flight Logs card does not use it.

    1. Something Happens in the C Module: Code in USBCommunication.c (the command port functions or the stream thread) calls log_event(source, level, format, ...) next to the printf that describes the event.
    2. The Entry Is Built: log_event formats the message, escapes it, adds a local timestamp, and wraps everything in a small JSON string.
    3. The Entry Waits in the Log Queue: The JSON string is pushed onto a native circular queue that has its own mutex, so any thread can log safely.
    4. The Log Worker Polls: A dedicated worker thread in Electron calls getNextLogPacket() repeatedly and drains the queue.
    5. The Main Process Stores and Forwards: main.js appends every entry to logHistory[] and, if a window is listening, sends it over the logData IPC channel.
    6. The Preload Script Exposes It: preload.js makes the channel available to the page as window.backendAPI.onLogData and getLogHistory.
    7. The Page Renders It: log.js parses the entry, hands a copy to every registered log tap (used by the integration tests), and then renders a row in the Debug Log.
    log_event() (USBCommunication.c, any thread)
      -> log queue      native circular buffer, 128 slots
      -> log worker thread   addonWorker.js, polls getNextLogPacket()
      -> main.js       adds to logHistory[], sends "logData" to the window
      -> preload.js      backendAPI.onLogData / getLogHistory
      -> log.js        appendLogEntry()
        -> logTaps    every entry, unfiltered (integrationTests.js)
        -> Debug Log rows every entry rendered; the filter only hides rows

    Native C Logging

    Overview

    All logging in the C module goes through one function, log_event(). It was added so the Error Logging page can show exactly what the communication layer is doing, without anyone having to attach a console to the app. It is designed around three rules:

    • It is thread-safe. The command functions and the stream thread can call it at the same time.
    • It never blocks on the UI. Entries only go into an in-memory queue; the worker drains it later.
    • It mirrors the console. Every message that is printed is also logged, and the other way around.

    log_event()

    void log_event(LogSource source, LogLevel level, const char* format, ...);

    Each call does the following, in order:

    1. Format the Message: The message is built with vsnprintf into a 512-byte buffer, so anything longer than 511 characters is cut off.
    2. Escape It for JSON: json_escape() escapes quotes, backslashes, newline, carriage return, tab, and writes every other control character below 0x20 as a \u00XX sequence. This matters because text that arrives through a %s argument can contain raw control bytes. For example, Windows appends a carriage return and line feed to the text returned by sp_last_error_message(), and a raw control character makes JSON.parse on the page fail with “Bad control character in string literal”.
    3. Stamp It: The timestamp comes from GetLocalTime(), so it is the local time of the computer running the app.
    4. Build the JSON: The source, level, timestamp, and escaped message are written into a 1200-byte buffer.
    5. Print It: The entry is also printed to the console as [SW][INFO] message.
    6. Queue It: The JSON string is pushed to the log queue with log_queue_push().

    Note: Because log_event prints to the console itself, a message that also has its own printf appears twice in the console. That is expected. The one printf that must never be paired is the one inside log_event, which would recurse.

    Log Entry Format

    Every entry delivered to the frontend is a JSON string like this:

    {
      "source": "SW",
      "level": "ERROR",
      "timestamp": "2026-09-09 14:32:07",
      "message": "Port verification failed in populateAll()"
    }
    Field Description
    source SW or FW (see Levels and Sources)
    level INFO, TIMING, WARNING, or ERROR
    timestamp YYYY-MM-DD HH:MM:SS, local time of the computer at the moment the entry was logged
    message Human-readable text. Newlines are escaped in the JSON and shown as line breaks on the page. Truncated at 511 characters by the C module

    Levels and Sources

    Value Meaning Color
    INFO Normal events: device found, port verified, attempt started, streaming started Blue #5DADFF
    WARNING Recoverable problems: failed reads, handshake failures, stream CRC mismatches Yellow #F5C542
    ERROR Failures: all retries failed, port not found, invalid command, stream read error Red #FF6B6B
    TIMING Performance measurements, such as the Timing: line written after a valid response Pink #FF7AC6
    SW Created by the desktop side: port scanning, opening and closing ports, attempts, timing, verification results Purple #B78CFF
    FW The desktop noticed a problem with what the firmware sent, or did not send Green #3DDC97

    In practice the source is chosen like this. Use SW for things the desktop did or decided. Use FW for things observed about the firmware's side of the conversation: a short or missing read, a size mismatch, a CRC mismatch, an unexpected header, a CRC error reported by the firmware, or a stream read error.

    Note: Two retry causes in write_to_port() (“CRC mismatch — retrying” and “Unexpected response header”) are currently logged as FW / INFO, while the matching handshake and stream CRC failures are WARNING. Anything that triggers a retry should be a WARNING. This is more than cosmetic: the integration tests only attach WARNING and ERROR entries to a failed result row, so an INFO-level retry reason will not show up there.

    The Log Queue

    The queue is a circular buffer of heap-allocated JSON strings.

    • Size: LOG_QUEUE_SIZE is 128 slots. One slot is always kept empty to tell a full queue from an empty one, so it holds up to 127 entries.
    • When it is full: The oldest entry is freed and dropped, so a slow consumer still shows the most recent messages. This only matters if the poller falls behind.
    • Locking: The queue has its own mutex, separate from the stream queue (64 slots), so a flood of one can never push entries out of the other.
    • Lazy setup: The mutex is created on first use through InitOnceExecuteOnce. Logging can happen before streaming has ever started, and from any thread, so setup cannot depend on one known thread running first.
    • Reading: getNextLogPacket() removes and returns the oldest entry, or NULL if the queue is empty. The Node-API wrapper converts it to a JavaScript string and frees the C copy. The function is exported to JavaScript alongside the other five addon functions.

    Keeping the Log Readable

    • Hex dumps are one entry. The per-byte hex printouts of raw packets are logged through log_hex_bytes() as a single entry per packet. The text buffer is 512 bytes at three characters per byte, so very long packets are truncated in the log (the console still prints every byte).
    • Stream packets are throttled. Stream packets arrive at a high rate. Only one sample is logged per STREAM_LOG_INTERVAL_MS (60 seconds), shown as [STREAM] Sample packet: {...}. The first packet of a session is always logged. This only affects logging: every packet still goes into the stream queue and reaches the UI through getNextStreamPacket(). Without the throttle the stream would flood the log queue and push real errors out of it.
    • Retries are visible. write_to_port() logs Attempt N... at the start of every attempt, so a command that needed two retries shows three of these lines before its result.
    • Responses are logged. The JSON a command returns is logged as JSON Response: followed by the text (still subject to the 511 character cut).

    Adding or Changing a Log Message

    1. Pair it with the printf: Put a log_event next to any new printf so the console and the page agree.
    2. Choose source and level: Follow the conventions above. Retry causes are WARNING.
    3. Never pass dynamic text as the format: Use log_event(..., "%s", text).
    4. Treat the wording as a contract: The integration tests recognize several messages by their first words. If you reword one of the messages below, update the matching pattern in integrationTests.js.


    Messages the Tests Depend On

    Message starts with Source / level Emitted by Used by the tests for
    Attempt N... SW / INFO write_to_port(), once per attempt Counting attempts and retries
    Valid response received SW / INFO write_to_port() Marks a successful call's logs as complete
    Timing: SW / TIMING write_to_port(), after the line above Phase timing shown on the result row
    All retries failed SW / ERROR write_to_port() Marks a failed call's logs as complete
    Invalid header in ... SW / ERROR populateAll, updateValue, startStreaming Completion of the unknown-command test
    Port verification failed SW / ERROR populateAll, updateValue Completion when no device is found
    Failed to find to COM port / Failed to open to COM port SW / WARNING write_to_port() Completion when the port cannot be opened
    Reconnection to port failed SW / ERROR write_to_port() Completion after a failed reopen
    Testing COMx... SW / INFO find_com_port() Detecting that a port re-scan happened
    Streaming started, Stream already running, Command port verification failed, Stream port verification failed, Failed to send start-streaming ..., Failed to create ... SW startStreaming() Completion of the stream start call
    Streaming stopped, Stream is not running SW / INFO stopStreaming() Completion of the stream stop call

    Note: “Failed to find to COM port” and “Failed to open to COM port” are written exactly like that in the C file (the extra “to” is a typo there). The test pattern matches the text as emitted. If the C wording is ever fixed, change the pattern in IT_DEFAULT_TERMINALS at the same time.

    Worker & IPC Layers for Logs

    Dedicated Log Worker

    Log polling runs on its own worker thread in main.js, separate from both the command worker (populateAll / updateValue) and the stream worker (getNextStreamPacket). This was intentional. The quaternion stream is polled at about 60 fps, and logs need to be drained continuously and independently of whatever the user is doing on other pages. Sharing a worker with either of those could delay log delivery or, worse, delay stream and command responses while waiting on a log poll.

    let logWorker = null;
    let logPendingRequests = new Map();
    let logHistory = [];  // persists across page navigation for the session
    const MAX_LOG_HISTORY = 500;

    function getLogWorker() { /* creates or reuses the log worker */ }
    function runInLogWorker(method, args) { /* posts a message, resolves on response */ }

    Each worker thread loads the native module with require(addonPath). Windows loads a given DLL path into a process once and shares it across threads, so all three workers operate on the same static state inside the C addon. This is the same reasoning that already applied to verified_port and port_verified being shared between the command and stream workers, and it is why the log queue can be filled by one thread and drained by another.

    Continuous Polling

    Log polling starts once, at app startup, and runs for the life of the app. It is not tied to the user opening the Error Logging page, so entries from the whole session are captured. The poll loop runs on a slower interval than the stream poll loop. Every entry that comes off the queue is:

    • Pushed into logHistory
    • Sent immediately to the renderer through the logData IPC channel, as long as a window is currently listening

    Note: logHistory is in memory only, so it resets when the app restarts.

    Log History

    ipcMain.handle("getLogHistory", () => {
      return logHistory;
    });

    This lets a newly opened Error Logging page ask for everything that has happened so far in the session before it starts listening for live updates. logHistory is capped at MAX_LOG_HISTORY (500), so the page can only recover the most recent 500 entries.

    Preload Bridge

    Four log-related methods are part of the backendAPI object exposed in preload.js:

    getLogHistory: () => ipcRenderer.invoke("getLogHistory"),
    onLogData: (callback) => ipcRenderer.on("logData", (event, packet) => callback(packet)),
    offLogData: () => ipcRenderer.removeAllListeners("logData"),
    saveLogFile: (logFile) => ipcRenderer.invoke("save-log-file", logFile)

    getLogHistory is a request and response call, onLogData is the push channel for live entries, offLogData removes the listener when the page closes, and saveLogFile hands a finished text file to the main process (see Saving Log Files).

    Error Logging Page (Frontend)

    Page Layout (log.html)

    The page has five cards. See the overview section above for what each card is for.

    OSCAR Ground Station Debug Log Filter

    The Filtering Options panel (#logFilterPanel) sits above the Debug Log and is always visible. It has source checkboxes (SW, FW), level checkboxes (INFO, TIMING, WARNING, ERROR), and a Reset button (#logFilterReset) that re-checks everything. Everything is shown by default.

    How it works:

    1. Checkbox Changes: Each checkbox carries data-filter="source" or data-filter="level" plus a value. Changing one updates the matching set (activeSources or activeLevels) and calls applyLogFilter().
    2. Existing Rows: applyLogFilter() toggles the log-filtered-out class on every existing row, then scrolls the list to the bottom.
    3. New Rows: New rows are checked against the filter as they are created, so they arrive already hidden or visible.
    4. Visibility Rule: A row is shown only if both its source and its level are enabled. A source or level that is not in the known lists is always shown, so odd entries cannot disappear.

    The filter is view-only. It does not change logHistory, the row cap, or what logTaps listeners receive, so filtering the display never affects integration test results. Hiding rows does not remove them, and turning a checkbox back on brings them back. It does affect the saved Debug Log file (see Saving Log Files).

    To add a new level or source later:

    1. Add it to KNOWN_LEVELS or KNOWN_SOURCES in log.js.
    2. Add its checkbox in log.html, with data-filter and a value that matches the uppercase name.
    3. Add its color variable and .log-<name> or .src-<name> styles in log.css.
    4. Add it to the level or source conventions in this document and, if the C module can emit it, to the LogLevel or LogSource enum and the name functions in USBCommunication.c.

    Saving Log Files

    The Save Debug Log button (saveGroundStationLogs) saves the OSCAR Ground Station Debug Log to a plain text file. It follows the same pattern as Save Configuration on the Load & Save page: the renderer collects the data, and the main process shows the save dialog and writes the file. The difference is that the output is formatted like the on-screen log rather than as JSON.

    The renderer never touches the file system. It only passes the finished text and a suggested file name to the main process.

    What gets saved

    • Only the visible rows. The text is built from the rows in #logList that are not hidden by the filter (.log-entry:not(.log-filtered-out)), so the file matches the screen. To save everything regardless of the filter, change the selector in collectGroundStationLog() to .log-entry.
    • Only what is on the page. Rows trimmed past MAX_LOG_ENTRIES (5000) are gone. After navigating away and back, the page reloads only the last 500 entries from main.js, so a save in that case holds at most 500 lines plus anything logged since.
    • Empty log. If there are no visible rows, nothing is saved and the error modal shows “There are no log entries to save.”

    File format

    One line per entry, in the same field order as the page:

    [timestamp] [SOURCE] [LEVEL ] message

    [2026-09-09 14:32:07] [SW] [INFO  ] Connected to flight controller
    [2026-09-09 14:32:09] [FW] [WARNING] Battery voltage low
    [2026-09-09 14:32:11] [SW] [ERROR ] Port verification failed in populateAll()
    • The level is padded to 7 characters (the length of WARNING) so messages line up.
    • If an entry has no timestamp, the timestamp bracket is left out.
    • Multi-line messages are written as they appear on the page, so they span several lines in the file.
    • Lines end with a line feed. Switch to carriage return plus line feed if users open files in older Windows Notepad.

    File name and dialog

    • The default name is oscar-debug-log-<timestamp>.txt, where the timestamp is the ISO time with : and . replaced by - (those characters are not allowed in Windows file names).
    • The save dialog (titled “Save Log”) offers Text Files (.txt) and Log Files (.log).
    • If the user cancels, the handler returns { canceled: true } and nothing happens.
    • Any error thrown while collecting or writing is shown through showError() in errorHandler.js.

    Implementation notes

    • main.js imports fs as require("fs/promises"), so the handler must call fs.writeFile(...). fs.promises.writeFile does not exist with that import and will throw.
    • The IPC channel name save-log-file must match in preload.js and main.js.
    • The Integration & Regression Tests card does not use this path. Its Save Test Results button builds a Blob in the renderer and downloads it (see Results Rows and Saved Report).

    Display Limits

    Where Setting Limit Behavior when exceeded
    C log queue LOG_QUEUE_SIZE 128 slots (127 usable) Oldest entry dropped; only matters if the poller falls behind
    C log message message buffer 511 characters Message is cut off
    main.js history MAX_LOG_HISTORY 500 Caps what getLogHistory() returns; in memory only, resets on app restart
    log.js page MAX_LOG_ENTRIES 5000 Oldest rows removed from the page
    Debug Log save file none of its own whatever is on the page Limited by the two caps above

    Because getLogHistory() is capped at 500 by main.js, raising MAX_LOG_ENTRIES alone will not show more history when the page loads. To see more past entries, raise MAX_LOG_HISTORY as well. Live entries keep accumulating on the page (up to MAX_LOG_ENTRIES) for as long as it stays open.

    Integration & Regression Tests

    Overview

    The Integration & Regression Tests card runs real commands against a connected drone to check that the firmware and OSCAR Ground Station communicate end to end. It is driven by integrationTests.js, not log.js, and it calls the same window.backendAPI functions the rest of the app uses (populateAll, updateValue, startStreaming, stopStreaming, onStreamData). For each call it reports pass, fail, or skip, the round-trip time, and how many attempts and retries the C module needed. When the run finishes it adds summary statistics. The same card is used for both integration testing (does a new command work) and regression testing (did a firmware or software change break an old one).

    This section explains how the card works internally. The testing documentation covers how to set up and use each testing method, including how to read the results.

    How the Tests Read the Logs

    The C addon only returns a response string. It does not return retry counts or phase timings. To get them, the test runner reads the same live log stream as the Debug Log:

    1. Register a Tap: Before each call, the runner adds a listener to logTaps (from log.js). Every incoming entry, parsed and unfiltered, is copied to it.
    2. Time the Call: The call is timed from the moment it starts to the moment its promise resolves. This is the round-trip time shown on the row.
    3. Wait for the Final Log Line: Log entries reach the page over IPC some time after the call returns. Instead of a fixed delay, the runner waits until a terminal line for that call has arrived (see below), polling every 25 ms for up to 3000 ms and then allowing 30 ms of grace. This keeps one call's attempts from being counted against the next call.
    4. Wait for the Timing Line: write_to_port() logs its Timing: line just after Valid response received. If the success line has been seen but the timing line has not, the runner waits up to 1500 ms for it. If it never arrives, the runner decides this build does not emit timing lines and stops waiting for it on later calls.
    5. Summarize the Logs: The runner counts Attempt N... lines for attempts, takes the first Timing: line, sets a re-scan flag if any Testing COMx... line appeared (the port had to be rediscovered), and collects every WARNING and ERROR message as log issues.
    Constant Value Meaning
    IT_LOG_TIMEOUT_MS 3000 How long to wait for a call's terminal log line
    IT_LOG_POLL_MS 25 How often to check for it
    IT_LOG_GRACE_MS 30 Extra wait after it arrives, so trailing lines are captured
    IT_TIMING_WAIT_MS 1500 How long to wait for the Timing: line after a valid response

    The terminal lines are the last message the C module logs for a call. They are kept in three pattern lists in integrationTests.js:

    • IT_DEFAULT_TERMINALS for populateAll and updateValue: valid response received, all retries failed, invalid header, port verification failed, failed to find or open the COM port, reconnection failed.
    • IT_STREAM_START_TERMINALS for startStreaming: streaming started, stream already running, invalid header, command or stream port verification failed, failed to send the start command or create the thread or mutex.
    • IT_STREAM_STOP_TERMINALS for stopStreaming: streaming stopped, stream is not running.

    Because of this design:

    • The Debug Log filter has no effect on test results.
    • If log forwarding is unavailable, or the terminal line does not arrive within the timeout, attempts and retries show as n/a and the call counts as a single attempt in the statistics.
    • Rewording any of the C messages in the table under Messages the Tests Depend On requires updating the matching pattern.

    Test Plan

    The plan is the INTEGRATION_TESTS array. Tests run in array order, filtered to the groups the user has enabled.

    Group What it does Default Tests
    read Getters only, plus one deliberate-failure test. Always runs and cannot be unchecked On 13
    settings Writes back the value the device just reported, so there is no net change On 6
    streaming Starts, samples, and stops each data stream On 2
    calibration Calibration and reset commands. May overwrite stored data Off 8
    motors Motor commands. Remove props first. May change motor configuration Off 15

    Each entry has a kind that decides how it runs:

    Kind Runs Used by
    populate backendAPI.populateAll(command) Getters in the read group
    update backendAPI.updateValue(command, payload) Calibration and motor commands, and the unknown-command test
    roundtrip Reads a value from an earlier response, then writes it back with updateValue The settings group
    stream Start, count packets, stop The streaming group

    Entries can use the following fields:

    Field Purpose
    group, kind, command Which group, how to run it, and the command string passed to the backend
    payload Value sent by update tests (empty string for commands that take none). On a round trip it forces the value instead of reading it
    expect List of checks on the parsed response. "Key" means the key must exist anywhere in the response. "Key=Value" means it must exist and equal the value, case-insensitive. Any miss fails the test as an unexpected response
    expectError The test passes only if the call returns an error (used for the unmapped command test)
    preflight If this test fails, the rest of the run is aborted. Set on GetConnection
    source, valueMap, numericOnly Round-trip settings, explained below
    extraStop, extraExpect Stream tests: a command to send after the normal stop, and the checks for its response
    quirk Marks a response that passes today but looks wrong. It is shown as a warning on the row and in the summary so it is not forgotten. When the firmware is fixed the expect check will fail, which is the cue to update expect and remove quirk

    Note: Command names in the plan must match map_command() in the C file exactly, including its spelling. For example the firmware version getter is GetFrimwareVersion in both places.

    Running a Test Run

    runIntegrationTests() is the entry point for the Run Integration Tests button.

    1. Second Click Means Stop: If a run is already in progress, the click sets an abort flag and the status line reads “Stopping after current call…”. The run stops after the call in flight finishes.
    2. Confirm Risky Groups: If calibration or motors is enabled, a confirmation popup tells the user to remove all propellers and warns that the commands can change motor settings or overwrite calibration data. Cancelling ends the run before anything is sent.
    3. Reset State: The report is cleared, the results list is emptied, and the UI switches to its running state: the button reads Stop Tests, Save Test Results is disabled, and the group checkboxes are locked.
    4. Run Each Test: The status line shows Running i/n: command. Before each test the abort flag is checked. One test can produce several result rows (a stream test produces start, data, and stop rows).
    5. Summarize: The statistics rows are added, the status line shows Complete or Aborted with the counts, and the UI returns to its idle state.

    If the page is closed mid-test, a pagehide handler stops any active stream so the drone is not left streaming.

    Judging a Response

    For populateAll and updateValue calls, itEvaluateResponse() decides whether a usable response came back:

    • A null result or an empty string is a failure (“No response (null)” or “Empty response”).
    • A string that is not valid JSON counts as received and passing, with a “non-JSON response” note.
    • An object with an ERROR key (case-insensitive) is a failure, and the error text becomes the failure reason. This is how “No device detected” and “Communication failed” from the C module show up.
    • Otherwise the response is received. Successful populateAll responses are stored in ctx.responses for the round-trip tests.

    Then the expect checks run against the parsed response. Key lookups search nested objects (up to five levels deep), ignore case, and ignore stray spaces around keys. A passing row shows a preview of the response, cut at IT_PREVIEW_CHARS (140) characters.

    The unknown-command test (NotARealCommand) is a negative test. It passes only if the call returns an error. It is reported in the summary on its own line and excluded from every count and percentage.

    Settings Round-Trip Tests

    The settings group changes real settings, so it is built to leave them exactly as they were. For each test the runner:

    1. Looks up the response of the getter named in source.command (for example GetInitialValuesVolt). If that read did not succeed, the test is skipped.
    2. Searches that response for any of the keys in source.keys (up to four levels deep, first simple value wins). If none is found, the test is skipped.
    3. If a valueMap is set, converts the display text the device reports into the option value the page sends. For example “Onboard ADC” becomes adc. An unmapped value is skipped.
    4. If numericOnly is set and the value is not a number, skips the test. This protects against writing display text to a field that expects a raw number.
    5. Sends the value back with updateValue and checks the expect list (for example SetMinCellVoltage=Done).

    A skip is a warning row, not a failure. A test is skipped rather than writing a guess to the drone. Setting an explicit payload on a test bypasses the lookup.

    Note: The pilot and drone name tests write back the name string as reported. These are the string inputs that the planned maximum size values apply to (see Maximum Input Sizes).

    Streaming Tests

    A stream test checks the whole stream path, not just one packet. For each stream command it:

    1. Checks the API: If startStreaming, stopStreaming, or onStreamData is not exposed by the preload script, the test is skipped.
    2. Counts Packets: It clears any old stream listener, then registers one that counts packets and records when the first one arrives after the start call returns.
    3. Starts the Stream: startStreaming(command) must return true. This call is timed, but its time is excluded from latency statistics because it includes stream-port discovery.
    4. Samples: If the start passed, it waits IT_STREAM_SAMPLE_MS (2000 ms). The data check passes if at least IT_STREAM_MIN_PACKETS (1) packets arrived, and its row reports the total, the count in the window, the approximate rate per second, and the time to first packet.
    5. Stops the Stream: stopStreaming() must return true. If the start failed, the stop row is a skip. Stop is also excluded from latency statistics because it waits for the stream thread to finish.
    6. Cleans Up: The listener is removed, and the stream is stopped again if it is somehow still active.
    7. Extra Stop: If extraStop is set, that command is sent afterwards as a normal updateValue test. This is needed because stopStreaming() always sends the quaternion stop command (0x8501), so the receiver stream's own stop command (StopReceiverStreamData) has to be exercised separately.

    Results Rows and Saved Report

    Each call has one row in the results list. A row first shows RUN while the call is in flight, then is redrawn in place with the final verdict. Row color follows these rules:

    • Red (error): the test failed.
    • Yellow (warning): the test passed but needed a retry, needed a port re-scan, or has a known quirk. Skips are also yellow.
    • Blue (info): a clean pass.

    A result line has fields separated by |: the call, its duration, attempts and retries, a re-scan note if one happened, the Timing: text, any reason, and a response preview. A failed row also includes the last two warning or error log lines captured during the call.

    The Save Test Results button downloads a text report. Only final rows go into it (not the temporary RUN rows), each as [time] [tag] text, after a header with the date and the enabled groups. The file is built as a Blob in the renderer and downloaded directly, so it does not use the save-log-file IPC path or the save dialog that the Debug Log uses. The default name is oscar-integration-tests-YYYYMMDD-HHMMSS.txt. If there are no results yet, an error is shown instead. The button is disabled while a run is in progress.

    Summary Statistics

    When the run ends, a ----- Statistics ----- row is followed by these summary lines. Executed tests are those that were not skipped.

    Line How it is calculated
    Totals Counted tests, passed, failed, skipped, and run time. Expected-error tests are not counted
    Pass rate Passed divided by executed tests
    USB communication accuracy (packet level) Successful device calls divided by total attempts across all device calls. A call with unknown attempt data counts as one attempt
    First-try success Device calls that passed with no retry, divided by all device calls
    Retries Total retries, average per call, and the call with the most retries
    Attempt data warning Shown if any call had no attempt data (final log line not received in time)
    Latency Average, median, 95th percentile, minimum, and maximum of passed calls. Streaming start and stop are excluded. Percentiles use the nearest-rank method
    Slowest The three slowest executed calls
    Streaming note Start and stop times, listed separately because they are not comparable to a command round trip
    Known quirks One note per passed test that has a quirk
    Expected-error test Pass or fail of the negative test, reported separately
    Failures and skips One FAILED row per failed call with its reason and one SKIPPED row per skip, or “No failed calls.”

    Note: A call that gets a valid response but fails its expect checks counts as failed in the accuracy and first-try numbers, so those two percentages measure correct responses, not just delivered packets.

    Keeping the Tests Up to Date

    The tests are only as accurate as the plan, the expected keys, and the log patterns. Update them whenever any of these change:

    • A New Firmware Command: Add it to map_command() in the C file, then add an entry to INTEGRATION_TESTS in the right group with an expect list that matches the JSON the firmware returns.
    • A Changed JSON Key or Value: Update the matching expect entries. A stale expectation shows up as an unexpected response failure.
    • A Reworded C Log Message: Update the matching pattern in the terminal lists or in the summary code (Attempt, Timing:, Testing).
    • A New Stream: Add a stream test, and an extraStop if it has its own stop command.
    • A New Group: Add the group to the plan, add a checkbox with data-test-group in log.html, and add the confirmation text if the group is risky.

    Where to Find More

    Test groups, how to add or update tests, how to read the results, and the regression workflow are covered in the Integration Testing and Regression Testing sections of the testing documentation.

    Onboard Flight Logs (Firmware Based Logs)

    Overview

    The Onboard Flight Logs card shows logs recorded and stored by the drone's firmware, including events from times when the drone was not connected to the desktop app. Unlike the OSCAR Ground Station Debug Log, these are not streamed live and they do not go through the C log queue or the log worker. They are historical data the desktop app asks the firmware for.

    Decisions

    • Logs are stored in the EEPROM. The firmware saves its log entries in EEPROM so they survive power loss and disconnects.
    • The user requests the logs with a button. The page no longer reads them automatically when it opens. This replaces the earlier plan of reading them once on page load.
    • Storage is shown. The card displays how much log storage is used and how much total storage there is.
    • The user can clear the stored logs. A button erases the stored log data after the user confirms.
    • Every number and string input gets a maximum size. See Maximum Input Sizes.

    Flight Log Flow From the Desktop

    To view more from the firmware side of the implementation, see the Firmware USB Communication documentation.

    1. Page Opens: The card shows the empty-state text. The storage line (used and total) is requested so it is filled in without loading any log entries.
    2. User Clicks Request Flight Logs: The button is disabled while the request is in progress so the user cannot send it twice.
    3. Request Goes Out: The renderer calls an exposed backendAPI function, which travels through IPC to the command worker and the C module. Flight logs are ordinary request and response commands, so they use the same path as populateAll, not the log worker.
    4. Firmware Replies: The firmware reads its EEPROM and returns the stored entries, in one packet or several.
    5. The Card Fills In: The entries are rendered into #flightLogList using the same four-field row layout as the Debug Log, with the source set to FW.
    6. Storage Refreshes: The used and total values are updated.

    Clearing the logs. When the user clicks Clear, a confirmation popup explains that the stored logs will be permanently erased. On confirm, the clear command is sent. On success the list is emptied and the storage line is refreshed. On failure the error is shown through showError() and the list is left as it was.

    Saving the logs. Save Flight Logs reuses the same save path as the Debug Log (backendAPI.saveLogFile and the save-log-file IPC channel) with a default name such as oscar-flight-log-<timestamp>.txt. If nothing has been loaded, it shows an error instead of saving an empty file.

    Commands

    View all the commands for this in the Firmware USB Communication documentation.

    Maximum Input Sizes

    Every number and string input in the app gets a defined maximum size. Many of these size limits are implemented in the frontend.

    Item Max Size
    Strings 16 bytes
    Toggles 1 byte
    Standard Integer Values 1 byte
    Motor Throttle Integer Size 2 bytes
    Voltage Displays 2 bytes
    Decimal Values 2 bytes

    Onboard Firmware Unit Tests

    Overview

    The Onboard Firmware Unit Tests card triggers tests that are built into the firmware and shows what the drone reports back. The tests run on the drone, and the desktop only starts them and displays the results. It is driven by firmwareTests.js, which shares helpers with the Flight Logs card through logShared.js. For what each test checks and how the firmware runs it, see the firmware unit testing documentation.

    This card is different from the Integration & Regression Tests card:

    Integration & Regression Tests Onboard Firmware Unit Tests
    Where the tests run On the desktop, one command at a time On the drone
    What is checked That a command gets a correct response Whatever the firmware's own tests check
    Who decides pass or fail The desktop (expect checks) The firmware, reported in its reply
    Uses the C log queue Reads it through logTaps No

    Desktop Flow

    1. User Clicks Run: The button is disabled and the status line shows that the tests are running.
    2. Trigger Goes Out: The renderer calls a backendAPI function that sends the trigger value to the firmware. Like the Flight Logs, this is an ordinary request and response command. It goes through IPC to the command worker and the C module, not the log worker.
    3. Firmware Runs and Replies: The firmware runs its tests and returns the results.
    4. Parse: A parser function in firmwareTests.js turns the reply into a list of results.
    5. Render: Each result becomes a row in the results list, using the same row layout as the other cards with the source set to FW. The row tag is PASS, FAIL, or SKIP.
    6. Summarize: A summary row follows the list, and the button returns to its idle state.

    Results and Saving

    • Rows: Each test has one row with its tag, name, and any detail text the firmware sent.
    • Summary row: It shows the counts for passed, failed, and skipped tests.
    • Save Test Results: It saves the results as a text file, similar to the Integration & Regression Tests card.

    Configuration (firmwareTests.js)

    The file opens with a config block and parser functions, so the firmware hookup can be changed in one place.

    Setting Purpose
    Command name The command string sent to the firmware to start the tests
    Trigger value The payload sent with the command
    resultsCommand Optional. For a two-step design where the firmware acknowledges the trigger immediately and the desktop then requests results with a second command
    JSON keys Where the parser looks in the reply for each test's name, status, and detail
    ready When false, the button shows a “not hooked up yet” message instead of sending an unknown command

    Logging Error Handling

    The logging system is designed to fail quietly so that a logging problem never stops the app from talking to the drone. These are the behaviors to expect:

    • Queue full: the oldest entry is dropped and nothing else is affected. The stream throttle exists to make this rare.
    • No window listening: entries still go into logHistory, so a page opened later can load them, up to 500.
    • Page opened late or app restarted: only the last 500 entries of the session are available. A restart clears everything.
    • Unparseable entry: it is shown as an SW / INFO row with the raw text instead of being dropped.
    • Unknown level or source: the row is shown with INFO styling and is never hidden by the filter.
    • Message too long: it is cut at 511 characters by the C module.
    • Backend API missing: log.js uses optional calls, so the lists simply stay empty. The integration tests report attempts as n/a, and they refuse to run if populateAll or updateValue is unavailable.
    • Save failed or nothing to save: the error is shown in the error modal through showError().
    • Console fallback: because log_event also prints, a build run with a console still has the full output there.
