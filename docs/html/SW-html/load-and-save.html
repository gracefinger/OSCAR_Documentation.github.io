    Load & Save

    UI Setup

    This document explains how configuration values are gathered and displayed in the OSCAR Ground Station UI Load and Save page, how the Save workflow exports them to a JSON file, and how the Load workflow validates and applies a file to the flight controller.

    Pages involved

    Load & Save is a summary and file-management page. The values it presents come from the other configuration pages; it does not query the controller for all of them itself.

    Page Configuration group Examples
    Home config Pilot name, Drone name
    Motors motors Mixer type, motor direction, ESC protocol, motor stop, ESC sensor
    Power & Battery battery Meter sources, cell-voltage thresholds, battery capacity
    Receiver receiver Stick Settings (Min, Center, Max)

    These pages include Components/configurationState.js. The Load & Save page includes Components/loadAndSave.js. Their roles are different: configurationState.js keeps the shared cache synchronized from settings pages, while loadAndSave.js drives the Load & Save page's preview, export, and import interactions.

    What the two scripts do

    configurationState.js: collect and cache settings

    This shared helper is used by the source settings pages. It does not retrieve values from the controller, populate the form, or itself send a controller command. Instead, it reads controls after the page-specific code has populated them and mirrors their values into the main process's configuration cache.

    It has four main responsibilities:

    • Convert controls into cache values. getConfigurationSettingValue() serializes a checkbox as "1" or "0", takes trimmed text from a SPAN, and otherwise reads the control's .value.
    • Keep readable labels separate from the actual setting JSON value. Selects record the selected option's visible text; checkboxes use the data-display-on or data-display-off label. These display-only values are used by the preview and are not a substitute for the underlying setting.
    • Send a page snapshot. cacheFrontendConfiguration() scans the current document for [data-setting][data-group], builds nested group/key objects for settings and labels, and sends them to window.backendAPI.cacheConfiguration().
    • Send incremental changes. Document-level input and change listeners call cacheChangedConfigurationSetting(). Controls without both required metadata attributes are ignored, and an annotated control sends a one-setting update when it changes.

    The page-specific scripts (home.js, motors.js, and powerBattery.js) perform their page's hardware reads and UI population, then call cacheFrontendConfiguration() so the initial controller values are cached. Their existing change handlers send user edits to the controller; the shared cache listeners separately mirror those edits to the cache. Caching a setting is not the same operation as writing it to the flight controller.

    loadAndSave.js: present, export, and import configuration

    This script is loaded only on the Load & Save page and wires its controls to the preload API. Its primary operations are:

    • Refresh the preview. On DOMContentLoaded, refreshConfigurationPreview() reads the cache and updates every preview element annotated with data-setting, data-group, and data-source-page. It shows Unset when the cached group/key is missing, null, or empty, and otherwise prefers a saved display label over the raw value.
    • Prepare an export. collectCurrentConfiguration() checks that every setting represented in the preview exists in the cache. It reports missing source pages. If complete, it removes displayLabels and creates the versioned object with formatVersion, savedAt, and settings. The Save button asks for confirmation, then calls window.backendAPI.saveConfiguration() to open the native save dialog and write the file.
    • Build import rules from the UI. For Load, the script asks the main process for the Home, Motors, and Power & Battery HTML. It parses the annotated controls and derives each setting's type, allowed select values, numeric constraints, controller command, display labels, and writable or unsupported status from their HTML attributes.
    • Validate and apply an import. It parses and validates the selected JSON, normalizes values, separates writable operations from recognized unsupported settings, and presents a review dialog. Only after confirmation does it check the controller and send the supported settings one at a time. It mirrors successful writes into the cache, refreshes the preview, and reports completion, skipped settings, or partial failure.

    This script handles the configuration file and review UI; controller communication is mediated by backendAPI and the main-process IPC handlers. It does not directly access Node.js or the serial addon.

    HTML metadata identifies settings

    Each included setting control in the source-page HTML uses:

    • data-setting — the setting's key, such as mixerType.
    • data-group — its section, such as motors.
    • Optional metadata such as data-cmd, data-cmd-on, data-cmd-off, data-cache-only, and data-config-loadable — used to determine how, or whether, a setting can be sent to the controller.

    The Load & Save page has display-only elements marked with data-setting, data-group, and data-source-page. The first two identify the cached value; data-source-page identifies which settings page provides it. The preview currently shows Personalization, Motor Configuration, and Battery Configuration, including Motor 1 and Motor 2 battery values.

    Page initialization and value capture

    When a settings page loads, its page-specific script requests values from the backend/controller and populates the controls. For example, Home calls populateAll("GetHomePageData"), and Power & Battery calls populateAll("GetInitialValuesVolt").

    Once controls are populated, the page calls cacheFrontendConfiguration() to send a snapshot of all controls on that page that have both data-setting and data-group. The snapshot is organized by group and setting key. Checkboxes are stored as "1" or "0"; other controls contribute their current value. Selects and checkboxes can also contribute a display label, which is kept separate from the underlying value so the preview can show human-readable text while the configuration file retains the actual setting value.

    configurationState.js also listens for input and change events. When an annotated control changes, it sends that one value to the cache. The page's own script separately handles controller updates for normal user edits; the cache listener's role is to keep the Load & Save snapshot current.

    Renderer-to-main-process path

    The configuration cache is maintained in memory by Electron's main process, not in a file and not in the Load & Save page itself:

    Settings page controls
    -> configurationState.js
    -> window.backendAPI (preload.js)
    -> Electron IPC
    -> main.js in-memory configuration cache
    -> Load & Save preview / Save workflow

    preload.js exposes a limited set of methods to the renderer, including cacheConfiguration() and getCachedConfiguration(). main.js stores configuration values and display labels in separate config, motors, and battery objects. The Load & Save page requests the cache when it initializes and uses it to update the preview. A missing, null, or empty-string preview value is displayed as Unset.

    The cache lasts only for the current application session. It is not a durable record of the controller's settings and is not automatically restored on a later launch. Open the settings pages in the current session so they can populate the cache before saving. Save checks the preview's declared settings and reports the source pages whose values are missing; merely seeing the Load & Save page does not cause those source pages to be queried.

    Save Feature

    What Save includes

    Save exports the values currently in the in-memory cache. It does not make a fresh all-settings controller request when the Save button is clicked. The configuration is assembled from the cache groups (config, motors, and battery), with the displayLabels property removed before serialization. Exported values are only as current as the values captured by the settings pages and their change listeners during this session.

    Save workflow

    • Open Home, Motors, and Power & Battery during the current session so their settings can be read and cached. Set the required settings from each page.
    • Open Load & Save. Its preview displays cached values using display labels when available; uncached or unset values display Unset.
    • Select Save Configuration. The app checks that each setting represented by a preview card is present in the cache. If any are missing, saving stops and an error identifies the source page or pages to open.
    • Review the prompt, Have you reviewed your selected settings? This is a confirmation step, not a second detailed listing of the values. Check the page's preview before continuing.
    • Select Continue to open the native save dialog. Choose where to save the JSON file. The suggested filename is oscar-configuration.json.
    • The main process serializes the configuration as formatted JSON and writes it to the selected path. Canceling either confirmation or the save dialog exits without writing a file.

    JSON format

    A saved file has this top-level shape:

    {
  "formatVersion": 1,
  "savedAt": "2026-01-01T00:00:00.000Z",
  "settings": {
    "config": {
      "PilotName": "Pilot",
      "DroneName": "Research Quad"
    },
    "motors": {
      "motorDirection": "0",
      "escProtocol": "value-from-the-selected-option"
    },
    "battery": {
      "MinCellVoltage": "3"
    }
  }
}

    The example values are illustrative. formatVersion identifies the supported file schema. savedAt is generated as an ISO timestamp when Save runs. The settings property contains the grouped cached values. Display labels are not written to the file, and fields are represented by setting keys rather than UI captions. Values are stored as JSON values; many controls contribute strings, including checkbox values represented as "1" or "0".

    The file may contain settings that are useful to preserve or show in the preview but cannot currently be written back to the controller. Such settings can be saved; Load identifies and skips them during its review/apply flow.

    Load Feature

    Selecting and parsing a file

    • Open Load & Save and select Choose Configuration File.
    • Select a file with a .json extension. Files larger than 1 MB are rejected.
    • The renderer reads and parses the file as JSON. Invalid JSON is rejected before the controller is contacted.
    • The renderer requests the source-page HTML for Home, Motors, and Power & Battery from the main process. It derives import rules from those pages' editable controls and metadata rather than relying on a separate hard-coded list of commands.
    • The file is validated and converted into controller operations and a separate list of settings recognized but unsupported for controller writes.
    • If there is at least one supported operation, the review dialog opens before any controller connection check or setting write. Its title includes the selected filename, and its summary states the number of supported settings that will be sent.
    • If the file also contains recognized settings that cannot be written, the dialog shows a Not applied section. It names each skipped setting and explains why it is unsupported. A safety warning reminds the user to remove propellers, check that the values fit the aircraft, and verify the setup before flight.
    • Choose Apply Settings only after reviewing the listed values and skipped items. The controller is contacted only after this confirmation. Choose Cancel, use the close button, or dismiss the dialog to stop the load without sending settings. If validation finds no supported operation, the app rejects the file instead of showing an empty review.

    File and value validation

    The root must be an object with formatVersion: 1 and an object-valued settings property. The only accepted top-level keys are formatVersion, savedAt, and settings. Within settings, each group must be a known configuration group and contain an object of setting keys and values. Unknown settings are accepted as unsupported legacy settings, provided the group structure is valid

    Control type Accepted values and checks
    Checkbox true, 1, "1", or "true" normalize to "1"; false, 0, "0", or "false" normalize to "0".
    Select The value must match one of the select's option values.
    Number The value must be a finite number, satisfy declared min and max, and align with the declared step when applicable. It is normalized to a numeric string.
    Text The value must be a string with no null character and at most 4088 UTF-8 bytes.

    Unknown root fields, groups, setting keys, malformed setting structures, unsupported format versions, and invalid values reject the entire file rather than silently applying a partial interpretation. A setting identified by the source-page metadata as non-writable is handled as an unsupported item, not as an operation to send.

    Review dialog

    Before any settings are sent, the app shows a review dialog titled with the selected filename. It groups supported operations under sections such as Personalization, Motor Settings, and Battery Settings. It reports how many supported settings will be sent and displays their setting names and values, using select/toggle labels where available.

    When the file contains recognized but non-writable settings, the dialog adds a Not applied section with the setting and the reason it will be skipped. The dialog includes a safety warning to remove propellers, confirm the values are appropriate for the aircraft, and verify the setup before flight. Selecting Cancel or closing the dialog cancels the load; the controller has not been contacted. If the file yields no supported operations, Load is rejected because there is nothing it can apply.

    Controller writes and progress

    After the user selects Apply settings, the app first calls populateAll("GetHomePageData") as a controller connection check. If that response is invalid or reports an error, the load stops. Otherwise, supported operations are sent one at a time through backendAPI.updateValue().

    For ordinary settings, the command comes from data-cmd when present, or defaults to the setting key. For boolean controls with data-cmd-on and data-cmd-off, the selected command depends on whether the normalized value is on or off. The normalized value is sent as the operation payload. The status indicator reports progress, such as Applying 2 of 5 settings....

    Some HTML metadata makes an otherwise recognized setting non-writable:

    • data-cache-only — the setting is for local configuration state, not a controller write.
    • data-config-loadable="false" — the source page explicitly disables loading that setting to the controller.
    • A non-editable or unsupported control type — no supported write operation can be created.

    These settings appear in the review dialog as skipped and remain unchanged on the controller. Saving a value in a file does not guarantee that the current controller can accept it.

    Completion, partial application, and cache updates

    Each successful controller write is recorded. If all writes succeed, the app updates the corresponding values in the in-memory cache and refreshes the Load & Save preview. The final status reports the number applied and, if relevant, the number skipped.

    Writes are sequential, not transactional. If a write fails, the app stops sending later operations, preserves the settings already written, reports which setting failed and how many succeeded, and does not roll back the controller. The status identifies the result as Partially applied.

    If controller writes succeed but the cache/preview update fails, the UI reports that the controller was updated even though the local preview could not be refreshed; it does not describe that situation as a complete local success.

    Safety and Practical Notes

    • Loading can immediately change values on the connected flight controller. Carefully inspect the review list and skipped settings before applying.
    • The application recommends removing propellers before applying a file.
    • After loading, verify the configuration and the aircraft's setup before operating the drone.
    • Use OSCAR configuration files. The file extension alone does not make an arbitrary JSON document a valid OSCAR configuration.
    • The Load & Save cache is in-memory and session-scoped. Save a JSON file if a durable copy is needed between application sessions.

    Load & Save Settings Maintenance

    The Load & Save page has two separate setting lists:

    • The save list is the set of elements in HTML/loadAndSave.html with data-setting, data-group, and data-source-page.
    • The load list is generated from the controls in each source page. A control with data-cache-only or data-config-loadable="false" is accepted as legacy input but is skipped instead of being written to the controller.

    Reproducible change procedure

    To remove a setting from both the save requirements and controller-load requirements:

    • Find the setting control in its source page, such as HTML/motors.html.
    • Keep its data-setting and data-group attributes if the source page still uses the setting at runtime.
    • Add data-config-loadable="false" when the setting must not be written by configuration loading. Use data-cache-only instead for a frontend-only cached value.
    • Remove the setting's entire preview .configuration-setting block from HTML/loadAndSave.html. Do not leave a commented preview block behind.
    • Add or update a regression case in test/loadAndSave.test.js covering the setting's skipped-load behavior.
    • Run npm test from Software/OSCAR-app.
    • Search the application for the setting name and confirm it remains only in runtime code, source-page controls, tests, or documentation as intended.
